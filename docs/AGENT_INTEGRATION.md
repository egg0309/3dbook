## 一、前端已经做了什么

- 书打开后，右下角出现“进入历史推演”；点击后从右侧滑出推演面板（移动端全屏）。
- 开场旁白与老陈的第一句台词由前端直接渲染，不调用接口（与产品文档一致）。
- 三个关卡各 4 个选项，以键盘可访问的按钮卡片呈现；点击发送代号（`1A`…`3D`）。
- 自由输入框保留：用于“复盘”指令，也用于展示非选项输入的兜底逻辑。
- 后端返回 `nextStage` 后，前端切换到下一关，并继续用本地脚本渲染对应的 4 个选项。
- 复盘：三关结束后出现“生成推演复盘”按钮，也可输入“复盘”；后端返回 `report` 后，以纸质报告卡呈现。
- 请求失败/超时会显示错误条和“重试”，重试会重发同一请求，不会丢关卡状态。
- 本地 Mock 模式可完整走通全流程（默认开启），方便后端未就绪时演示。

## 二、运行模式与切换

前端只读取两个环境变量：

| 变量 | 默认值 | 说明 |
|---|---|---|
| `VITE_AGENT_MODE` | `mock` | `mock` 使用前端内置演示；`live` 调用真实接口 |
| `VITE_AGENT_API_URL` | `/api/chat` | 接口路径或完整 URL |
| `VITE_AGENT_PROXY_TARGET` | `http://127.0.0.1:8000` | 仅开发/预览：Vite 把 `/api` 代理到该地址 |

### 本地切到真实后端

1. 在 `web/` 下复制 `.env.example` 为 `.env.local`：
   ```bash
   VITE_AGENT_MODE=live
   VITE_AGENT_API_URL=/api/chat
   VITE_AGENT_PROXY_TARGET=http://127.0.0.1:8000
   ```
2. 后端监听 `127.0.0.1:8000`，实现 `POST /api/chat`。
3. 重启 `npm run dev`。页面底部徽标会从“本地演示”变成“在线推演”。

### 生产环境

- 推荐前后端同源部署：Web 服务器把 `/api/*` 反向代理到后端，`VITE_AGENT_MODE=live`、`VITE_AGENT_API_URL=/api/chat`。
- 如果接口在独立域名：把 `VITE_AGENT_API_URL` 设为完整 URL，并在后端配置 CORS；Vite 的 proxy 只在 dev/preview 生效。
- **API Key 只能放在后端**，不要写进 `VITE_*`、前端代码或浏览器请求。
- `VITE_AGENT_MODE` 是构建时变量，修改后需要重新构建。

## 三、接口契约

### 3.1 请求

`POST /api/chat`，`Content-Type: application/json`。

```json
{
  "sessionId": "9b8f0c8e-...",
  "stage": "level1",
  "choice": "1A",
  "message": "可选，自由输入内容",
  "choices": {
    "choice_1": "1A",
    "choice_2": "2A",
    "choice_3": null
  }
}
```

字段说明：

| 字段 | 类型 | 何时出现 | 说明 |
|---|---|---|---|
| `sessionId` | string | 总是 | 前端每次打开/重置推演生成的 UUID；可用于日志/会话 |
| `stage` | `level1` \| `level2` \| `level3` \| `review` | 总是 | 当前正在作答的关卡；复盘时为 `review` |
| `choice` | `1A`…`3D` | 点击选项卡片时 | 当前关卡选择的代号 |
| `message` | string | 自由输入/复盘 | 自由输入文本；复盘时为 `"复盘"` |
| `choices` | object | 总是 | 已累计的前两关（或全部三关）选择；方便后端无状态计算 |
| `choices.choice_1/2/3` | `1A`…`3D` \| 缺省 | 按进度 | 注意：点击当前选项时，`choices` 里还没有这一次的选择，后端应把 `choice` 与 `choices` 合并理解 |

> 建议后端按“`stage` + `choice`”路由到产品文档里对应的 LLM Prompt。`sessionId` 不是必需的，前端已经把关键状态放在请求里，后端可以无状态实现。

### 3.2 响应

```json
{
  "reply": "老陈的台词，纯文本",
  "nextStage": "level2",
  "report": "仅 nextStage=done 时返回的复盘正文",
  "fallback": false
}
```

| 字段 | 类型 | 必需 | 说明 |
|---|---|---|---|
| `reply` | string | 是 | 老陈（或兜底）台词；纯文本，可含换行，禁止 Markdown/JSON/思考过程 |
| `nextStage` | `level1` \| `level2` \| `level3` \| `review` \| `done` | 是 | 答复后的阶段；选项卡片由前端按该阶段渲染 |
| `report` | string | `done` 时必需 | 个性化复盘正文；纯文本，可含空行 |
| `fallback` | boolean | 否 | 非选项输入的兜底标记；建议同时让 `nextStage` 保持当前关 |

前端校验：

- `reply` 为空会显示错误并允许重试。
- `nextStage` 缺失时前端会按“有 choice 则进下一关、无 choice 则停留在当前关”做兼容推断；但**请后端明确返回**，避免歧义。
- `nextStage=done` 但缺少 `report` 会被前端判为接口错误。
- 非 2xx、非 JSON、字段类型错误、12 秒超时，都会进入错误条 + 重试。
- 重试会重发同一个 payload；后端应尽量幂等，不要在失败/重试时重复扣费或重复推进会话。

### 3.3 阶段流转

| 当前 `stage` | 输入 | 期望 `nextStage` |
|---|---|---|
| `level1` | `choice=1A/1B/1C/1D` | `level2` |
| `level2` | `choice=2A/2B/2C/2D` | `level3` |
| `level3` | `choice=3A/3B/3C/3D` | `review` |
| `level1/2/3` | 非选项自由文本 | 原 `stage` + `fallback:true` |
| `review` | `message="复盘"` | `done` + `report` |
| `review` | 其他文本 | `review` + 兜底台词 |

> 选项本身不需要后端返回；标签固定在前端脚本里。如果后端想返回额外选项，请先与前端约定，当前版本不会读取。

### 3.4 示例

**第一关点 1A**

```bash
curl -X POST http://127.0.0.1:8000/api/chat \
  -H "Content-Type: application/json" \
  -d '{"sessionId":"demo","stage":"level1","choice":"1A","choices":{}}'
```

```json
{
  "reply": "凯丰说毛泽东同志只照着两本书打仗……你说，这问题出在哪？",
  "nextStage": "level2"
}
```

**自由输入兜底**

```json
{
  "sessionId": "demo",
  "stage": "level2",
  "message": "今天天气不错",
  "choices": { "choice_1": "1A" }
}
```

```json
{
  "reply": "老陈疑惑地看了看你：“小同志，发什么愣呢！……”",
  "nextStage": "level2",
  "fallback": true
}
```

**复盘**

```json
{
  "sessionId": "demo",
  "stage": "review",
  "message": "复盘",
  "choices": { "choice_1": "1A", "choice_2": "2A", "choice_3": "3D" }
}
```

```json
{
  "reply": "老陈把一张写满字的纸递给你……",
  "nextStage": "done",
  "report": "你最后选择了独立思考、实事求是……"
}
```

## 四、后端如何接产品文档里的 Prompt

后端拿到的 `stage` 与 `choice` 可以直接映射到源文档的节点：

| 请求 | 源文档节点 |
|---|---|
| `stage=level1`, `choice=1A` | 【1A】追问老陈“凯丰为什么这么说” → LLM 输出 Prompt |
| `stage=level1`, `choice=1B` | 【1B】问老陈“湘江到底损失了多少” |
| … | 同理到 3D |
| `stage=review`, `message=复盘` | 关卡四：复盘总结（把 `choices` 传给复盘 Prompt） |
| 其他自由文本 | 异常兜底逻辑：返回写死的兜底文案 |

- 老陈台词的全局 System Prompt、语气、字数、禁用 Markdown/JSON/思考过程等约束，全部以源文档为准。
- 前端已经渲染下一关的选项卡片，所以后端回复里**可以省略**“请回复 2A 或 2B”这类指令；如果保留，也不会破坏 UI，只是会和卡片重复。
- 复盘正文建议按源文档的“肯定与解析 / 精准点拨 / 可迁移启示”三段来写；前端会把换行渲染出来。
- 源文档要求台词不超过 100 字、复盘不超过 250 字；前端不会强制截断，请在后端 Prompt/校验中控制。
- 建议使用轻量模型并关闭流式输出，目标 2 秒内返回；前端超时是 12 秒。未来如要流式，需要额外改前端。
- 后端应对模型输出做校验：如果出现 Markdown、JSON、括号动作描写、编造党史内容等，直接回退到安全文案或重试。

## 七、已知限制与后续可扩展

- 目前是**单会话、内存态**：页面刷新后重新开始；如需续玩，可在 `useAgent` 里读写 `sessionStorage`，或让后端按 `sessionId` 持久化。
- 不支持流式输出；当前是一次性 JSON。
- 自由输入是次要路径，主要交互仍是选项卡片；后端应对自由输入统一做兜底/审核。
- 只有一个 NPC 老陈；后续可扩展多角色/多轮追问。
- 报告是纯文本；后续可做分享图/长图/收藏。
- 没有鉴权和限流；上线前请在后端加会话校验、频率限制、内容审核和成本控制。

## 八、安全与内容约束

- 前端不持有任何模型 Key；所有模型调用在后端。
- 用户自由输入属于不可信输入：后端要用系统 Prompt 约束“老陈”的认知边界，不执行用户注入的指令，不编造党史信息。
- 涉及真实历史人物时，保持庄重、克制，不做戏说、不渲染血腥；必要时输出兜底。
- 对接口做输入长度限制（前端 `maxLength=200`，后端仍需校验）、速率限制和超时。
- 推演内容标注“基于党史资料改编，仅用于教学；请以权威史料为准”，该文案已在前端面板底部展示。

## 九、立体书呈现契约（2026-11-06 定稿）

### 9.1 核心变化

故事开始后呈现 3D 立体书，**所有对话只出现在画面下部 1/4 区域，同一时刻只呈现一段，播完即走、不留历史、不滚动、不存档**（内部状态机仍保留消息与 choices，仅渲染层不回看）。上部 3/4 完全留给立体书，对话容器不拦截指针。右侧滑出的独立面板废弃。

### 9.2 布局分区（给前端的占位约定）

```
┌─────────────────────────────────────────────────────┐
│              3D 立体书（上部 3/4，无对话遮挡）         │
├──────┬──────────────────────────────────────────────┤
│ 左1/5 │ 下部 1/4 舞台（单段播放，二选一形态）：        │
│ 熊形象│  形态 A 背景段：[ 旁白文字，居中 ] [继续 ↓]   │
│ 常驻  │  形态 B 对话段：[老陈气泡] │ [问题+ABCD 选项] │
│      │             左右两栏等宽                       │
├──────┴──────────────────────────────────────────────┤
│  底部细输入条（胶囊形，固定，与内容区左缘对齐）         │
└─────────────────────────────────────────────────────┘
```

熊形象素材位于 `web/public/book/laoduizhang.png`（易班熊“老队长”，已抠除黑底的透明 PNG，由同名 jpg 边缘泛洪处理得到），在对话区左侧约 1/5 屏宽常驻（left 2vw、宽 20vw）、底部对齐；对话内容区左缘 18vw（按透明图实际视觉右缘避让），左气泡栏与右问题栏等宽。推演打开时左下角章节标题（`.chapter-meta`）自动上移至 bottom 53vh 避让熊形象。

### 9.3 消息角色 → 渲染通道（权威分流规则）

| 角色（`AgentMessageRole`） | 内容 | 渲染方式 |
|---|---|---|
| `narration` / `system` | 序章/过场/尾声旁白、系统提示 | 下部 1/4 **居中单段**，打字机播完后出现“继续”，点击才淡出进下一段 |
| `npc` | 老陈的引导语、选项反馈、自由问答回复 | 左侧常驻熊形象（老队长）+ 对话气泡；若当前有待作答关卡，气泡右侧同时出现问题与 ABCD |
| `user` | 用户点击的选项/自由输入 | **不回显、不留痕**，仅发送给后端；画面直接切到等待指示或老陈反馈 |
| 问题区（非消息流） | 关卡标题、focus、ABCD 选项按钮 | 对话段右侧，打字机播完后才亮起；作答后整段被下一段替换 |
| `report` 复盘 | 终章画像长评（`/api/chat` 返回的 `report`） | **唯一例外**：下部区域内一封可停留、可滚动的长信（呼应“老陈把写满字的纸递给你”），保留选项历程角标与“重新推演”动作 |

### 9.4 消息时序（状态机已保证，前端按序渲染即可）

```
旁白 narration（居中，点“继续”推进，可能多段）
  → 老陈引导语 npc 气泡（左）+ 问题与 ABCD（右，打字机播完才可点）
  → 用户作答：无回显，原段消失，显示“老陈正在斟酌…”
  → 老陈反馈 npc 气泡 + 下一关问题（同屏，反馈即下一问的语段）
  → ……三关结束 → 复盘卡（右侧）→ report 长信停留
```

参考实现：`web/src/features/agent/BookStageChat.tsx`（原型，类名前缀 `bsc-`，与旧 `agent.css` 独立）。

### 9.5 不变的东西（后端契约不受呈现改版影响）

- `POST /api/chat` 的请求/响应字段、阶段流转（3.3 表）、12 秒超时、幂等要求、`fallback` 逻辑全部不变。
- `AgentMessageRole` 的四分类（narration/npc/user/system）已能支撑新布局，**无需新增消息类型**，改的只是各角色的渲染容器。
- 选项标签仍由前端 `script.ts` 静态持有，后端不返回选项；后端只回台词、阶段和复盘。
- 老陈的人设、认知边界、Prompt 约束（纯文本、无 Markdown、字数限制）不变。
- 自由输入保留并移到底部固定输入条；其兜底/审核逻辑不变。

### 9.6 给前端的拆分建议（仅建议，不强制）

旧 `AgentPanel.tsx` 抽屉容器废弃。原型 `BookStageChat.tsx` 已验证可行：`useAgent.ts` 状态机和 `agentApi.ts` 原封不动复用，渲染层拆为单段播放器（旁白段/对话段两种形态）+ 复盘长信 + 底部输入条。正式版建议组件：`NarrationSegment`（居中背景段）、`DialogSegment`（左气泡+右选项）、`ReportLetter`（可停留长信）、`BottomInput`（胶囊输入条），并保留播放指针（当前段下标）与打字机 hook。

### 9.7 待确认/占位事项

1. 单段播放默认不回看；复盘长信是唯一可停留滚动的内容。若产品后续要求“翻看前文”，需另做消息历史入口，不在当前契约内。
2. 打字机节奏（现原型约 32ms/字）由前端调，后端仍为非流式一次性返回，不做 SSE。
3. 对话区向导形象已统一为易班熊“老队长”（`/book/laoduizhang.png`，透明底），与 3D 场景 `Book.tsx` 的 bear 弹窗形象同源；如后续替换正式立绘，只需替换该素材，容器尺寸（宽约 1/5 屏宽）不变。
4. 后续多章节（八章架构）的章节切换、章节小复盘沿用本契约；新增内容类型时先改本表再开发。

### 9.8 入场探索阶段（2026-11-06 新增，纯前端状态，接口契约不变）

推演面板打开后不再直接进旁白，而是先进入**探索阶段**，强制玩家点完立体书室内的全部 4 个热点机关后才解锁“开始推演”：

```
打开推演 → 老陈引导语（固定文案，打字机）：先伸手推开立体书上的大门，线索都在会场屋内
  + 探索卡（x/4、四个圆点，提示“先推开大门进屋，再点击屋内的四处机关”）
  → 玩家点击建筑触发推门运镜进入室内，逐个点击四处热点，
    每个热点弹出原有的 BookDialog 档案，对应圆点点亮
  → 4/4 全部点亮 → “开始推演”按钮解锁 → 进入 9.3/9.4 的既有推演时序
```

> 推门是 3D 层既有交互（点击 `building` 图层触发 `startRoomEntry` 运镜），探索阶段不改 3D 行为，只靠引导语和卡片提示把玩家引到门口。
>
> 由于 3D 机关本身没有可点击高亮，探索卡在进度为 0/4 时额外显示一条带跳动上箭头的金色胶囊提示“点击上方立体书上的大门，推门进屋”（`.bsc-explore-cue`，`pointer-events:none` 不挡 3D 点击）；玩家点到任意第一个热点后提示自动消失，下方常驻文案列出屋内四个目标及其右下角集中的位置。

约定：

1. **4 个热点 id 固定在前端** `script.ts` 的 `HOTSPOT_IDS`：`zunyi_people`、`zunyi_crates`、`zunyi_stove`、`zunyi_bag`，均为推门后的室内机关，与 `Book.tsx` 的 `POPUP_DIALOGS` 键对应。
2. 门外的 `bear`（老陈立像）仍是可点击的 3D 机关、弹窗照旧，但**不计入探索进度**——它在推门前才能点到，计入门禁会导致玩家进屋后卡在 4/5 无法解锁。
3. 热点 id 由 3D 层经 `onOpenDialog(id, title, content)` 向上透传，`App.tsx` 用 `Set` 记录已看热点（重复点不重复计数；不在 `HOTSPOT_IDS` 内的 id 只弹窗不计数），再以 `visitedHotspots`/`totalHotspots` 两个 props 传给 `BookStageChat`。
4. 老陈的探索引导语是 `script.ts` 里的静态常量 `EXPLORE_OPENING`，**不调用 LLM、不发任何请求**；探索阶段底部输入条禁用。
5. 解锁条件为 `visitedHotspots.length >= totalHotspots`（强制 4/4，无跳过入口）。同一会话内点“重新推演”不再强制重看（会话内记忆 `everExploredRef`）；刷新页面后探索进度与推演进度一同重置。
6. **后端无感知**：不新增请求字段、不新增阶段，`/api/chat` 的请求/响应、阶段流转、超时与幂等要求全部不变；探索阶段后端收不到任何流量。
7. 多章节化后，每章的热点 id 清单与探索引导语按章挂在前端脚本中，仍由前端静态持有，不需要后端配合。
